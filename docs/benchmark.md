# Physics benchmark: how many drones can we fly?

Generated by `python scripts/benchmark.py`. Times one call of `mindflight.physics.dynamics.step` for the
whole swarm (dt = 2 ms), hovering, with no autograd. **drone-steps/s** = N × steps/s.
**real-time ×** = steps/s × dt: at 1.0 the swarm flies as fast as real time. **vs eager** compares a
faster mode with the plain step on the same device and N. The graph stepper rows do 10 physics steps per call
(one 50 Hz policy action) and are reported per physics step, so they compare directly.

## Machine

- GPU: NVIDIA GeForce RTX 5090
- CPU: AMD Ryzen 9 7900X3D 12-Core Processor (12 torch threads)
- torch 2.11.0+cu128, CUDA 12.8, Python 3.13.7, Windows 11
- Each row: warm-up, then the median of 3 runs of at least 1 s
- Note: measured while three other PPO training runs shared this GPU and CPU (CPU ~70 % busy before we started).
  That hurts the eager GPU rows most, because eager is limited by the CPU launching kernels: they ran at ~155
  steps/s here against 650–730 on the idle machine in #15, so the "vs eager" ratios below are inflated about 4×.
  Against the idle eager numbers, the graph stepper (3.3–4.3 k steps/s here) is roughly **5×** and the graph
  stepper + compile (35–56 k steps/s here) roughly **50–75×**. Re-run on an idle machine for clean numbers.

## GPU vs CPU

The GPU pulls ahead from about **N = 16,384**: at N = 16,384 it does 2.49 M drone-steps/s against the CPU's 1.54 M (1.6× faster). Below that the CPU wins (N = 1: CPU 1,462 vs GPU 157 steps/s), because a step is about 215 tiny GPU kernels and the cost is launching them, not running them: at N = 4,096 a step takes 6.44 ms but the GPU is busy for only 0.454 ms (7%). That launch cost is the same for 1 drone or 16,384, so the GPU's steps/s stays almost flat as N grows while the CPU's time grows with N. The next section removes that launch cost.

## Where a GPU step's time goes

Eager steps at N = 4,096. Wall time is from the Results table below; GPU busy time and
kernel launches are from `torch.profiler` over 100 steps.

| wall time per step | GPU busy per step | GPU busy | kernel launches per step |
|---:|---:|---:|---:|
| 6.436 ms | 0.454 ms | 7% | 215 |

## Fast path: CUDA graphs and torch.compile

Recording 10 physics steps as one CUDA graph (`CudaGraphStepper`) removes the CPU's launch cost: 20.9× at N = 4,096 and 22.6× at N = 16,384 over the eager GPU step, with bit-identical results. The graph still runs every tiny kernel one after another, each with a few µs of GPU start-up and its own trip through memory; letting torch.compile fuse them first (`compile=True`) is another 10.1× and reaches 567.07 M drone-steps/s at N = 16,384 (228× eager).

Training should use `CudaGraphStepper(n, "cuda", substeps=10, compile=True)` from `mindflight/physics/fast.py`
(it falls back to the graph alone if triton is missing); the plain `step` stays the readable reference.

## Why `torch.compile` (inductor) may say "not available"

Inductor writes new fused kernels at run time. For CUDA it needs the `triton` package (on Windows, for torch
2.11: `pip install "triton-windows<3.8"`), and for CPU it needs a C++ compiler (on Windows: MSVC from the
Visual Studio Build Tools, run from a Developer prompt). Without them the row above records the error instead
of a time. A CUDA step only stays free of the C++ compiler if it does no CPU work at all: before the motor
layout, gravity and inertia were kept on the GPU (`mindflight/physics/device_cache.py`), that small CPU math
made inductor ask for MSVC even on CUDA. The `cudagraphs` backend and the graph stepper need neither tool,
but they too can only record a step that never copies from the CPU; if a row says "graphs not captured",
that row is plain eager speed.
